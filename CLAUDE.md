# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

**TBY SMART APP** — A Streamlit business management app deployed on Streamlit Community Cloud for a Zhulian MLM distributor. It replaces manual spreadsheets for: recording sales/orders, shipping (iShip integration), tracking outstanding balances (ค้างจ่าย/ค้างรับ) and PV points, daily company-transfer/commission finance, stock counts, and Shopee/Lazada/TikTok e-commerce profit tracking. Backend is Supabase (PostgreSQL). No local dev server needed for testing — changes go live via `git push origin main`.

## Running & Deploying

```bash
# Local development
streamlit run app.py

# Deploy: just push — Streamlit Cloud auto-deploys from GitHub main branch
git add . && git commit -m "..." && git push origin main
```

Dependencies: `pip install -r requirements.txt`

Credentials live in `.streamlit/secrets.toml` (local) and Streamlit Cloud Secrets (production). Required keys: `SUPABASE_URL`, `SUPABASE_KEY`. Optional: `ISHIP_TOKEN` + iShip sender address fields, `LINE_CHANNEL_ACCESS_TOKEN`, `APP_PASSWORD` (enables a simple password login gate — see Authentication below), `DEBUG_MODE` (shows raw API-response debug expanders when truthy). No e-commerce API credentials needed — Shopee/Lazada/TikTok are all file-upload based (see 🛒 E-commerce below), not OAuth.

## Tests

`tests/` — unittest suite for `calc_logic.py`, `flash_zones.py`, `carriers.py`. Run: `py -m unittest discover -s tests -v` (pytest not installed, use stdlib unittest).

## Authentication

If `APP_PASSWORD` is set in secrets, `app.py` shows a password form before rendering anything and gates on `st.session_state["_authenticated"]`. No per-user accounts — one shared password for all staff. If `APP_PASSWORD` is unset, the app has no login gate at all.

`DEBUG_MODE` (secret) toggles visibility of raw-response `st.expander`s (iShip create/label responses, etc.) used for troubleshooting integration issues in production.

💵 การเงิน        — fin_ui.py: 💰 ยอดขาย (daily finance), 📑 ใบเสร็จ/เคลม VAT (commission + VAT)

## Business Logic by Tab

### 📋 บันทึกรายการ (`record_ui.py`)

- **📝 บันทึกขาย**: pick/quick-add customer, paste product codes (`_parse_quick_order`) or edit an `st.data_editor` cart, optionally receive outstanding items from old bills in the same flow (`db.get_pending_receipts_for_customer` + `_process_old_items_receipt`), set delivery status (ส่งพัสดุ/ฝากของ/รับแล้ว) and pay status (ค้างจ่าย/จ่ายแล้ว/COD/จ่ายบางส่วน). Saves a batch of transaction rows (`db.insert_transactions_batch`); partial payment is split proportionally across cart lines by `line_total/cart_total` share, with the **last row absorbing the rounding remainder**, and fully-paid lines flip to `จ่ายแล้ว`.
- **📦 ส่งของ**: shipping-only — no product/sales rows, cart items are informational only for weight/iShip payload. Saves straight to `db.create_shipment(source="ship")`.
- **🔢 คำนวณยอด**: parses LINE-OA-style order text (`calc_logic.parse_calc_order`, e.g. `TF2581-2 RB2306-1 SH-kg12170 COD`), shows customer-facing quote vs. actual cheapest carrier cost (`carriers.get_shipping_options`), can push the quote via LINE, trigger a trial iShip order, and includes a box-packing planner (`carriers.plan_boxes`). A dedicated "แผนคะแนน (PV)" text input (`_calc_plan_v{ver}`, e.g. `2500 2500 1000` or shorthand `2500*2 1000`) — parsed by `calc_logic.parse_plan_target_list()`, no `plan` keyword needed — splits the ordered items across multiple sub-bills via `split_bills_by_pv()`, each landing as close as possible to its target PV (randomized greedy, 1000 attempts, ported line-for-line from `gas_line_webhook.js`'s `plan` keyword so the LINE OA bot and this tab agree on results), leftovers shown separately as "ยังไม่เปิดบิล". A `plan 2500 2500 1000` token embedded in the main order text (`calc_logic.parse_plan_targets()`) still works too as a fallback, for text pasted straight from LINE OA. Computed once per "คำนวณ" click and cached in `st.session_state["_calc_result"]["plan_result"]` — not recomputed every rerun, since the algorithm is randomized. **Dual quote when shipping method isn't specified**: if the customer just pastes product codes/qty with no `SH-kg`, no "📦 จัดส่ง" checkbox, and no COD (`_no_ship_info` flag), the customer-facing summary and the LINE-push text both show the product total (= pickup price, no separate "รับหน้าร้าน" line — it's the same number so a duplicate line was dropped) plus one icon-led delivery line: `💵 สินค้า (ဆိုင်မှာ လာယူပါ): ฿{total}` / `🚚📦 จัดส่ง (စံပို့ဆောင်မှု): +{ship_add} = ฿{deliver_est}` where `deliver_est = product_total + calc_shipping(weight, "")` (weight-only Flash Express estimate, **no** zone surcharge) — Thai labels carry a Burmese gloss in parens since most customers are Burmese and don't read Thai fluently. No computed remote-area/zone-surcharge number is shown (tried and dropped 2026-08-28 — real `zone_surcharge` in `flash_zones.py` is tiered tourist +30/remote +50/tourist_island +60 so a flat add-on number risked being read as precise when it wasn't); instead a static Burmese-only disclaimer (`_MM_REMOTE_NOTE` module constant in `record_ui.py`) says islands/mountain areas incur +50 and that the shop will follow up with the exact fee — the exact number is still resolved at the existing exact-quote step once "📦 จัดส่ง" + a real postcode is entered. `_MM_REMOTE_NOTE` is plain text (no markdown) so the identical string works both wrapped in `***...***` for the on-screen `st.markdown` and unwrapped in the LINE-push text (LINE doesn't render markdown). This exact dual-quote design (product line + one icon-led delivery line + `MM_REMOTE_NOTE`, no "ยอดโอนสุทธิ" line) is mirrored in `gas_line_webhook.js`'s own order-calculation reply (`doPost`, the `!hasShipping && !isCOD` branch) so the live LINE bot's auto-reply matches this Streamlit tab's wording exactly — both read from the same Burmese note text (kept as separate constants, `_MM_REMOTE_NOTE` in Python / `MM_REMOTE_NOTE` in JS, hand-synced). The bot's old behavior (shows the normal single "ยอดโอนสุทธิ" summary, then appends a static "ราคานี้ยังไม่รวมค่าจัดส่ง" disclaimer) is preserved for every other case — with shipping specified, or COD without shipping specified (an existing edge case, out of scope here).
- **📮 ส่ง Manual**: a separate, self-contained Inter Express box planner + manual (non-iShip) label printer with custom box-size presets, writing `db.create_shipment(source="manual")`. Has its own order-text input/parse/session-state (`st.session_state["_mbx_result"]`/`["_mbx_lines"]`) — does **not** read or share state with 🔢 คำนวณยอด (used to reuse `_calc_result` from that tab; decoupled 2026-08-28 since switching between the two tabs was overwriting each other's calculation unexpectedly). No postcode/`SH-kg` input at all — Inter Express in this flow is always a self-drop-off at the courier's counter (flat nationwide rate, `_no_sur` surcharge function in `carriers.py`, postcode has zero effect on price or `max_cm`), so `carr.get_shipping_options()`/`plan_boxes()` are always called with `postcode=""`.
- **iShip flow (shared by บันทึกขาย/ส่งของ)**: both stage a request into `st.session_state["_iship_carrier_select"]` (with `tab: "sale"/"ship"`) rather than calling `iship_api.create_order` inline — the actual dialog/order-create lives in `app.py`. On success, `_build_success_info` populates `_iship_success_info` (shared success dialog with a "ส่งแจ้งลูกค้าทาง LINE" button), and `_do_clear_after_iship` triggers a full form reset.
- **Key formulas**: COD fee = `ceil((product_total + ship_fee) × 0.0321)`, editable via a manual override input. Shipping base (`calc_shipping()`): Flash Express `39 ฿` for first 5kg + `10 ฿`/kg beyond, plus `zone_surcharge(postcode)`. `BOX_WEIGHT_G = 500` (0.5kg) is added on top of raw product weight everywhere shipping cost is computed — `raw_weight_g()` deliberately excludes it, don't double-add. Carrier auto-pick (`_pick_carrier`): Bangkok-area postcodes (`10`/`11`/`12` prefix) or weight > 3kg → SPX Express, else Flash Express.
- **Session-state patterns**: staging keys (`_fr_*`, `_fsp_*`) are popped into the real widget key before that widget renders next rerun (Streamlit forbids setting a widget's key after render). Cart persistence: the `st.data_editor` base DataFrame lives in `_cart_base`/`_sp_cart_base`, and the editor key is version-suffixed (`m_cart_{version}`) — bumping the version int + popping the old key is the reliable way to force-reset a data_editor.

### 🗂️ รายละเอียดบิล (`bill_detail_ui.py`)

- **💰 ยอดค้าง / จัดการบิล**: per-customer expanders grouped from `db.get_outstanding_df()`. Only the "active" customer (from search, or a flagged `_t5_out_active_cust`) gets its full action panel rendered — everyone else shows a collapsed static table (perf guard against rendering 20+ heavy panels every rerun). Multi-row select (`st.dataframe(selection_mode="multi-row")`) + a mode radio (กำหนดเอง / จ่ายเงินอย่างเดียว / รับของอย่างเดียว / เปิดบิลอย่างเดียว) drives a combo `st.data_editor` for recording payment/receipt across several rows at once. Also has bill/item delete and a bulk "✅ เคลียร์บิล" (mark several bills paid+billed at once).
- **👤 บัตรลูกค้า**: ledger view from `db.get_customer_ledger(cid)`; per-bill timeline with a delivery-method heuristic (🚚 ส่งพัสดุ if ship date matches order date, 🏪 รับหน้าร้าน if bill_no found in receipts, else 📦 ฝากของ); a "สรุปรายสินค้า" expander computes billed-vs-prepaid netting (`ค้างสุทธิ = ค้างจ่ายบิล − จ่ายล่วงหน้า`, and the reverse `เครดิตเหลือ`) plus an เบิกของ (unbilled+unpaid, grouped by product) table.
- **📋 ประวัติทั้งหมด**: full history / bulk-edit view. Editing qty/paid columns in the `st.data_editor` is diffed against the original row and turned into new `partial_events` (never a direct field overwrite, preserving audit trail) — only customer/product/bill&pay-status edits go through `db.update_transaction` directly.
- **🚚 ประวัติการส่ง**: syncs delivery status (`iship_api.get_shipment_statuses` → `db.update_delivery_statuses`) and COD-transferred status (`iship_api.get_cod_transfers` → `db.mark_cod_transferred`/`mark_cod_paid`); can resend to iShip (repopulates the shared `_iship_carrier_select` dialog in `app.py`) or reprint a label; manual (non-iShip) shipments reconstruct box/COD details by regex-parsing a `[กล่อง: ...]` tag stashed in `notes` (no structured box table for manual shipments).
- **Key formulas**: outstanding = `total_amount − total_paid` / `qty − total_received` (`db.get_transaction_balance`), summed across `partial_events` unless `pay_status` is already `จ่ายแล้ว`/`COD จ่ายแล้ว` (then treated as fully paid/received). `db.split_and_open_bill(txn_id, qty_to_open)` shrinks a ฝากของ row to the billed qty (marks เปิดบิลแล้ว) and inserts a sibling row for the remainder (still ยังไม่เปิดบิล). `ui_helpers._bills_from_df()` groups a transactions dataframe by `เลขที่บิล` (total/owed/pending-qty/is_paid/is_billed/pv_unbilled) — reused by ยอดค้าง, บัตรลูกค้า, and the shared print panel. `ui_helpers._render_bill_panel()` is the one shared print/LINE-summary template used for both single-bill and "รวมทุกบิล" prints — it detects shipped bills via a `[ส่งพัสดุ|carrier|postcode|น้ำหนัก=Xkg|ค่าส่ง=Y]` tag embedded in `หมายเหตุ`.
- **COD note**: COD amounts are excluded from "ค้างจ่าย"/LINE outstanding messages (tracked separately as owed_cod) since they're settled at delivery, not invoiced.

### 💵 การเงิน (`fin_ui.py`)

Three sub-tabs: **💰 ยอดขาย**, **📑 ใบเสร็จ/เคลม VAT**, and **🧾 ค่าใช้จ่าย**. The ภาษีซื้อ-ขาย feature described as "wishlist, not yet implemented" in earlier notes **is now implemented** — do not treat it as pending.

- **Daily entries** (`finance_daily` table, one row/day via delete+insert upsert): `transfer_amount` (โอนให้บริษัท), `sales_amount` (ยอดขาย รวม VAT), `po_amount` (PO สั่งของ, ไม่รวม VAT), `registration_fee`, `bv_amount`, `stock_value` (opening stock, set once via "เปิดเดือนใหม่"), `adjustment` (carry-forward), `notes`.
- **Running formulas** (`db.get_finance_df()`): `net = Σ(transfer + bv + adjustment) − Σ(sales + registration_fee)` (ยอดค้างโอน vs. เงินโอนเกิน); `auto_stock = opening_stock + Σ(po_amount) − Σ(sales_amount/1.07)`; **order credit limit** `สิทธิ์สั่งของ = (1,100,000 + net)/1.07 − auto_stock` — note the hardcoded ฿1.1M ceiling.
- **VAT**: ภาษีขาย (output VAT) = `sales_amount − sales_amount/1.07`; ภาษีซื้อ (input VAT) = `po_amount × 0.07` **plus** claimable VAT from `expense_records` rows with `has_tax_invoice=True` in the same month range (`amount − amount/1.07`, inclusive-VAT formula — same as `sales_amount`, NOT the PO exclusive-VAT formula); net = output − input ("ต้องจ่าย"/"ขอคืนได้"). Separately, commission VAT claim = `commission_amount × 0.07`, tracked in `commission_records.vat_claim_amount`.
- **🧾 ค่าใช้จ่าย** (`expense_records` table, insert/delete only — no edit-in-place in v1): loose receipts (fuel, meals, supplies, shipping, wages, rent/utilities, advertising, bank fees, vehicle lease, communications, local tax, misc — see `_EXPENSE_CATEGORIES` in `fin_ui.py`) logged as amount (VAT-inclusive) + category + optional vendor/notes + `has_tax_invoice` flag. Each category shows a non-binding Thai tax-deductibility caption (general guidance, not a ruling for this specific shop — accountant should confirm).
- **📊 กำไรโดยประมาณ** (estimated monthly profit, shown below the VAT summary in 💰 ยอดขาย, same month-range selector): `net_profit_est = offline_sales_ex_vat + ecommerce_net + commission_net_amount − po_ex_vat − all_expenses_total`. Deliberately mixes cash-basis (PO/expenses) with the E-commerce module's real settlement-based net and the Zhulian commission net (`commission_records.net_amount`, after WHT) — **not** a certified accrual P&L, always shown with a disclaimer caption. TBY's revenue model is agency/commission-based (11%/10% from Zhulian), not simple resale margin — see the `tby-accounting` skill (`.claude/skills/tby-accounting/SKILL.md`) before redesigning this formula.
- **Commission records** (`commission_records`, one row/period `YYYY-MM`): commission amount, WHT (withholding tax, default 3%), net amount, auto-incrementing receipt numbering per Thai Buddhist year (recomputed by scanning prior records, not a DB sequence), VAT-claim doc tracking fields. `company_info` table stores TBY + HQ tax-ID/address printed on receipts.
- **Printing**: `_render_receipt_html` builds a full A4 ใบเสร็จรับเงิน/ใบกำกับภาษี (incl. a Thai-baht-to-words converter), rendered via `components.html` + `window.print()` — no server-side PDF library.
- `commission_rls_fix.sql` (repo root) disables RLS on `commission_records`/`company_info` — these tables default to RLS-enabled-with-no-policy when created via the Supabase Table Editor, which blocks all inserts since the app has no per-user auth (single shared `SUPABASE_KEY`). `expense_records_setup.sql` follows the same pattern for the new table.

**`ecom_calc.settled_order_sns()` requires `net_amount > 0`, not just "a row exists" (changed 2026-09-21)** — found while debugging a user-reported TikTok "ขาดทุน" that turned out to be a real ฿1,085.83 payout per TikTok's own dashboard: a batch of ~22 `ecommerce_order_income`/`tiktok_order_income` rows imported 2026-07-21 (before the 2026-09-05 fix to `tiktok_income_import._get_any()`'s column-name fallback) had `net_amount`/`net_settlement` silently zeroed by the old bug, while other fields (`total_fees`, `product_subtotal_after_disc`) parsed fine from a different, unaffected column — so the row existed and "looked settled" at ฿0, and every downstream function treated ฿0 as a confirmed final loss instead of unknown/bad data. Old signature only checked `r["order_sn"] in income_rows`; a genuinely-completed order that happens to net exactly ฿0 is vanishingly rare in this shop's real data (zero confirmed real cases found vs. two confirmed bad-data cases in one debugging session), so the user decided to always treat `net_amount <= 0` (including `None`) as **still pending**, same as no income row at all. This one function feeds three call sites in `database.py` (`get_ecommerce_product_margin_df`, `get_ecommerce_pending_income_df`, `get_ecommerce_sales_df`) — all three had to add `net_amount` to their `.select("order_sn")` calls since the old code never needed the value, just presence. `_ecommerce_order_costs()` (order-anomaly/order-profit-summary path) doesn't call `settled_order_sns()` at all — it builds its own `incomes` dict — so it got the equivalent filter (`if float(r.get("net_amount") or 0) > 0`) applied directly when building that dict instead. Net effect: an order stuck at ₿0 income no longer shows as a confirmed loss anywhere — it now surfaces instead in the "ออเดอร์ที่ยังไม่มี Income มา match" pending list (`get_ecommerce_pending_income_df[_all]`) and in `get_ecommerce_sales_df`'s raw table as "รอโอน" (via `na_rep="รอโอน"` on the styled dataframe — was `"รอยืนยัน"` before, changed to match the user's exact wording).

**`ecom_calc.settled_order_sns()` refined again same day**: `net_amount != 0` was too broad — it swept up *real, confirmed* negative settlements (return penalties) as "still pending" too. Found live via order `#260723DMNYMNFR` (ts_shop56): buyer returned the item in full (`return_status`="คำขอได้รับการยอมรับแล้ว"), Shopee actually transferred `net_amount=-102.0` (a real settled loss, confirmed by `transfer_date`) — treating that as "pending" would have hidden a genuine loss from every anomaly/margin table. Final rule: **only `net_amount == 0` exactly** (not merely `<= 0`) counts as "still pending" — negative values are real, final settlements and count as settled same as positive ones.

## database.py Patterns

**Cache invalidation**: `_clear_transaction_caches()` clears all transaction-related caches at once (`get_all_transactions_df`, `get_outstanding_df`, `get_bill_summaries`, `get_unbilled_pv_summary`, `get_unbilled_received_qty_by_product`, `get_billed_not_received_qty_by_product`). Every mutation must call it. Other cached reads worth knowing about: `get_products`/`get_customers` (5 min), `_all_customer_addresses` (2 min), `get_customer_ledger`/`get_today_transactions`/`get_pending_receipts_for_customer`/`bill_has_partial_events` (~1 min), `get_finance_df`/`get_finance_summary`/`get_bill_list`/`get_latest_stock_counts`/`get_stock_deposits` (2 min), `get_commission_records`/`get_commission_record` (1 min), `get_company_info` (5 min).

**Retry wrapper**: All Supabase calls should go through `_retry(fn, attempts=2, delay=0.5)` to handle transient network errors.

**PostgREST `.in_()` limit**: URL length caps out around 50 IDs. All `.in_()` queries are batched in chunks of 50. Do not increase this — PostgREST will silently fail or return HTTP 414.

**PostgREST default 1,000-row page cap**: separate from the `.in_()` limit above — applies to *any* `.select()...execute()` call, even a plain `.eq()` filter with no `.in_()` at all. Supabase/PostgREST silently returns at most 1,000 rows per request with no error, no warning, and no indication in the response that more rows exist. Found 2026-09-06: Shopee shop `ts_shop56` alone has 1,800+ `ecommerce_sales` rows, so every E-commerce aggregation function that queried without a `shop_name` filter (i.e. "รวมทุกร้าน" — the common case) was silently working off a truncated ~1,000-row slice, and even `allocate_ecommerce_order_income("shopee")` (no `shop_name` param at all) was leaving ~2,174 `ecommerce_sales.net_amount` rows never allocated (stuck at 0) once Shopee's income rows passed 1,000 — this alone was inflating apparent losses across nearly every Shopee product by huge amounts (one real before/after: combined E-commerce net went from an apparent **-613,233 loss to a real +150,998 profit** after backfilling). Fixed via `database._fetch_all(build_query)` — pass a zero-arg function that returns a **fresh, already-filtered-and-ordered** query builder (not a built object — the same builder is safe to re-`.range()`+`.execute()` repeatedly, but `_fetch_all` still expects a callable per its own contract); it loops `.range()` until a page comes back short. Always add an explicit `.order()` (prefer a genuinely unique column: `id`, or `order_sn`/`order_id` where there's no bare `id`) before paginating — Postgres does not guarantee stable row order across separate paginated requests without one, so two `.range()` calls without `.order()` can double-count or skip rows. **Any new query against a table that could plausibly exceed 1,000 rows must use `_fetch_all`, not `_retry(lambda: q.execute()).data`** — this is easy to forget since it fails silently with no error at any row count. A full-system audit 2026-09-20 found the same unpaginated pattern outside e-commerce, on the core sales ledger: `get_all_transactions_df()` (the sole data source for `get_outstanding_df()` — ยอดค้างจ่าย/ค้างรับ — when called with no date filter, which is how the ยอดค้าง/บัตรลูกค้า pages call it), `get_bill_list()`, `get_bill_summaries()`, and `_all_customer_addresses()` were all plain unpaginated queries. Not yet actively truncating (`transactions` was 339 rows, `customer_addresses` 639 rows at audit time — both climbing steadily), but the exact same failure mode as the e-commerce incident above: once `transactions` crosses 1,000 rows, the **oldest unpaid bills would silently stop showing in ยอดค้าง** with no error. Fixed preemptively by switching all four to `_fetch_all` (each now carries a `.order("id")` tiebreaker too, since `bill_no`/`date`/`phone` alone aren't unique enough for stable pagination — ties across page boundaries can otherwise skip or duplicate rows).

**`allocate_ecommerce_order_income()` was also badly unscoped — found 2026-09-20 when a user-reported "upload is taking forever"** led back to it: every call recomputed **every shop on the platform**, not just the one just uploaded (no `shop_name` filter existed at all), *and* wrote one row at a time via `.update()` in a loop — one HTTP round-trip per `ecommerce_sales` line item, against 2,500+ Shopee `ecommerce_order_income` rows platform-wide, on every single Order.all/Income upload for any one shop. Fixed by (1) adding a `shop_name` param, now passed from every `ecom_ui.py` upload call site (Shopee order/income import, Lazada import, TikTok sync) so a single-shop upload only recomputes that shop; (2) batching the writes via `.upsert()` (500 rows/call) instead of one `.update()` per row. **Gotcha hit while fixing**: `.upsert()` with only `{id, net_amount}` in the payload throws `null value ... violates not-null constraint` even though the row already exists — Postgrest's upsert compiles to a real `INSERT ... ON CONFLICT DO UPDATE`, and Postgres validates NOT NULL columns while building the candidate INSERT row *before* conflict resolution ever runs, so omitted required columns fail immediately regardless of whether a conflict would occur. Fix: `select("*")` the full rows first, mutate only `net_amount` in memory, upsert the complete rows back. Verified against real data (tobeyoung, 699 rows): went from an unbounded multi-minute row-by-row loop to 5.6s, and allocated `net_amount` sums still match `ecommerce_order_income.net_amount` per order exactly.

**"Upsert" pattern for daily/period tables**: `finance_daily` and `commission_records` don't use real Postgres upsert — mutations delete the existing row for that key (`entry_date`/`period`) then insert the new one.

**`split_and_open_bill(transaction_id, qty_to_bill)`**: splits a ฝากของ transaction into two rows (billed qty vs. remaining), then marks the new row as เปิดบิลแล้ว.

**Corrections preserve audit trail**: bulk-edit flows (ประวัติทั้งหมด) never overwrite `qty_received`/`amount_paid` directly — they insert a new `partial_events` delta row so history stays reconstructable.

## Key Patterns

**Session state for widgets**: Streamlit widgets can't have their key set after rendering. Use staging keys (e.g., `_fsp_dt`, `_fr_dt`) that are applied to widget keys BEFORE the widget renders on the next rerun.

**Cart persistence**: `st.data_editor` stores only edit diffs relative to its initial DataFrame. Always keep the same base DataFrame in `st.session_state["_cart_base"]` across reruns — never re-initialize with an empty DataFrame while the user is mid-entry. Editor keys are version-suffixed (e.g. `m_cart_{version}`) so a full reset is done by bumping the version and popping the old key, not by clearing the DataFrame in place.

**Address autocomplete**: postcode→tambon and tambon→postcode both live in `ui_helpers.py` (`_postcode_suggest`, `_tambon_selectbox`), backed by `thai_address._load_tambon_index()` with `bangkok_addresses.py` as a fallback for ambiguous/Bangkok-adjacent postcodes.

**Saving customer addresses (`db.upsert_customer_address`)**: deletes by `id` first (edit-in-place case), then — if `phone` is set — deletes **every** existing `customer_addresses` row with that same phone number (regardless of `customer_id`) before inserting, so a phone number only ever has one saved address at a time; intentional, confirmed with the user 2026-09-01 (a re-save under the same phone means the address changed, so the old one should be replaced, not kept alongside). `get_address_by_phone()` (autofill when typing a phone in ส่งของ/บันทึกขาย) relies on this — only one row can ever match a given phone. `ui_helpers._warn_duplicate_phone()` warns before saving if the phone already has an address under a *different* customer_id, since saving will delete that other customer's address too.

**COD calculation**: `collect = total_amt + ship_fee + cod_fee` where `cod_fee = ceil((total_amt + ship_fee) × 3.21%)`, editable via a manual override.

**Customer IDs**: Always `C-NNN` format (e.g., `C-014`). Quick-add (in บันทึกขาย and จัดการข้อมูล) auto-generates the next C-NNN by scanning existing IDs for the max number.

**Bill numbers**: Format `YYMMDD-NNN` (e.g., `260427-001`). Generated by `db.get_next_bill_no(date_str)`. Column `bill_no` was added to `transactions` via ALTER TABLE — not in `supabase_setup.sql`.

**Shared iShip dialogs**: the carrier-select and success dialogs are defined once in `app.py` (`@st.dialog`) and driven purely by session-state (`_iship_carrier_select`, `_iship_success_info`) so any tab (บันทึกขาย, ส่งของ, ประวัติการส่ง resend) can trigger them by populating those keys and calling `st.rerun()`.

## LINE OA Integration

Customers register by texting `สมัคร 0812345678` to the LINE OA. A Google Apps Script (GAS) webhook (`gas_line_webhook.js`) handles this, queries Supabase for the matching phone number, and writes `line_user_id` back to the `customers` row.

Once `line_user_id` is set, the app can call `line_api.push_tracking()` after a successful iShip shipment, `push_outstanding()`/`push_bill_summary()` from รายละเอียดบิล, and `push_partial_receipt()` after partial payment/receipt — all gated on `line_api.is_configured()` and a non-empty `line_user_id` (optionally paired with a `group_id`).

Secrets needed: `LINE_CHANNEL_ACCESS_TOKEN` in Streamlit secrets (for push) and `SUPABASE_URL`/`SUPABASE_KEY` in the GAS script (for the registration webhook).

**`gas_line_webhook.js`** also handles LINE OA order-taking (bot-style conversational ordering, old-goods pickup menus, cancel buttons in every confirm menu) — this file is edited/deployed to Google Apps Script independently of the Streamlit app's git history; check its own inline comments/`LAST_ERROR` script-property debugging before assuming behavior matches what's deployed live.

**`gas_coffee_log_webhook.js`** (added 2026-09-21, source pasted by user) is a **completely separate** LINE OA + GAS bot for coffee serial-number stock tracking (`addcoffee`/`out` commands, writes straight to Google Sheets, no Supabase/TBY app involvement at all) — different Google account (praphatsorn.t@gmail.com) than the shop's main "zhulian TBY" OA (zhulian.ttby@gmail.com, backs `gas_line_webhook.js`). Kept in this repo purely as a backup/reference copy — the live version is deployed independently at its own Apps Script web app URL (see the file's header comment), and this repo's copy is not synced to it automatically. The user's original pasted source hardcoded a live `LINE_CHANNEL_ACCESS_TOKEN` in plaintext — **this repo is a public GitHub repo**, so that token was replaced with `PropertiesService.getScriptProperties().getProperty('LINE_ACCESS_TOKEN')` (same safer pattern as `gas_line_webhook.js`) before saving; the real token must be set as a Script Property directly on the live Apps Script project, never committed here. See [[coffee_line_oa_separate_system]] memory for the account mapping and the in-progress task of redirecting the daily email-digest LINE alert (`tools/email_daily_digest.py`) to go through this OA instead of the customer-facing one.
